orientation

What a SOC is, and what this one is

A SOC — Security Operations Center — is the function that continuously watches an environment for threats and responds. The industry builds it from people, process, and a stack of technology. socteam rebuilds the technology slice at home scale:

SOC pieceWhat it doesCommercial formsocteam form
NDR sensorwatches the wire, packets → meaningZeek, Suricatasensor crate — the core
SIEMstores + correlates eventsSplunk, Elasticstore (DuckDB, gated)
detectionsevents → alertsSigma rulesdetect (phase 2)
consolewhere a human triagesSecurity Onionconsole v0 — shipped
threat intelknown-bad indicatorsMISP, feedsopt-in feeds (phase 3)

The library core has outgrown the traffic light: the flow table (1B) folds bidirectional conversations, protocol parsers (1C) read DNS messages, HTTP header blocks, and TLS ClientHellos — SNI, ciphers, extension order — straight off the wire bytes, and the event pipeline (1D) now emits meaning: one Zeek-style stream of conn / dns / ssl / http / heartbeat records, written as rotating NDJSON. The remaining upgrades before the sensor is production-shaped are storage (1E) and the perf gate (1F).

The seam is a three-line trait. Everything downstream of it is source-agnostic:

// crates/sensor/src/source/mod.rs
pub trait PacketSource {
    type Item;
    fn next_packet(&mut self) -> Option<Self::Item>;  // None = clean EOF
}

Each item is a CapturedPacket — raw frame bytes, a capture timestamp, and the on-wire length (which can exceed the stored length when a capture snaps long frames). Live capture stamps arrival time; pcap replay maps file timestamps onto the same clock, so tests are deterministic.

The event stream (1D)

With --events <DIR> the sensor folds every frame through the flow table and the protocol parsers, and writes what it understood as tagged NDJSON — one JSON object per line, rotated to a fresh file before any line would push the current one past --rotate-bytes (16 MiB by default: an SD-card-friendly ceiling). Idle and half-open conversations are reaped by timeout into conn records with a Zeek-style state label; quiet seconds still produce a heartbeat so a silent sensor is distinguishable from a dead one.

engineering decisions

Choices that shape everything downstream

Pure core, I/O shell

count.rs does arithmetic on byte slices and nothing else — no network, no disk, no clock. Everything messy is pushed to the edges. The logic that matters is therefore testable with plain cargo test, no root and no hardware, which is exactly what CI runs on every push.

A trait between us and the hardware

Phase 2+ swaps the Linux backend to raw AF_PACKET rings with eBPF filters — kernel-side, near-zero-copy capture. Because sources live behind PacketSource, that swap touches one file and nothing downstream changes. The abstraction was bought for testing; it pays again for the low-latency path.

Threads and channels, not async

The reader thread plus an mpsc channel is the whole concurrency model — zero runtime overhead on the packet path and simpler to reason about. Async (tokio) enters exactly one place: the console's web server, where it belongs. The hot path stays sync by design.

Errors as data, never panics

Every frame is untrusted bytes from a network that may be hostile — that is the threat model of the sensor itself. Library code returns typed errors (thiserror), the binary adds context (anyhow). None strictly means clean end-of-stream; malformed input is Some(Err(_)). A parser crash is a remote DoS vulnerability wearing a different hat.

Synthetic fixtures only

Tests build packets in code and generate pcaps on the fly. Real captures never enter the repository — they can contain credentials, and a security repo that leaks its own network's secrets has failed at its one job.

CI as a gate, and the Pi as a first-class target

Every commit must pass formatting, clippy with warnings-as-errors, the test suite, and a cross-compile check for aarch64-unknown-linux-gnu — the Raspberry Pi's architecture. A change that breaks the deployment target cannot land silently on a dev-machine success.

current work

Console v0 — seeing what we have

The first window into the sensor: socteam-console serves a self-contained dashboard (no CDN, no framework) and streams one snapshot per second over a WebSocket, with a plain JSON endpoint as fallback. It shows what exists today — source kind, total frames, packets-per-second with a live sparkline, byte count, and the ethertype breakdown.

# sudo-free demo — the sim source generates plausible traffic
cargo run -p console --bin socteam-console -- --simulate
# real capture (needs root)          # replay a capture file
sudo socteam-console --iface en0            socteam-console --pcap capture.pcap

It binds to 127.0.0.1:8080 by default, and that is deliberate: there is no authentication yet, so the monitoring pane stays on loopback until auth exists. Exposing it to the LAN is a one-flag decision that waits for a security story.

the long game

Red and blue, one core

The end state is a platform where offensive tools test the defensive sensor they share genes with — a syn-scanner and a scan detector want the same packet builders, a spoof generator and an ARP-watch want the same L2 code. One parser core, two customers:

hard rule — from AGENTS.md
Red-team/attack tooling runs only against networks and hosts you own or have explicit authorization to test — never third-party systems. The red track does not start until the blue core (phases 1–2) is complete.
